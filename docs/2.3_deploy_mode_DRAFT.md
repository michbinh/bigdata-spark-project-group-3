## A. Deploy mode: `client` và `cluster`

### A.1. Vấn đề mà deploy mode giải quyết

Một ứng dụng Spark luôn gồm hai loại tiến trình:

- **Driver** — chạy hàm `main()`, dựng `SparkContext`, phân tích lineage, chia
  job thành stage/task, lên lịch và nhận kết quả trả về (ví dụ `collect()`,
  `take()`, `count()`).
- **Executor** — tiến trình worker thực thi task và giữ dữ liệu đã cache.

Executor **luôn** chạy trên các node của cluster. Điều duy nhất mà deploy mode
quyết định là: **Driver chạy ở đâu.**

```
client mode                              cluster mode
-----------------------------------      -----------------------------------
[Máy submit]                             [Máy submit]
  └── Driver  ◄──── kết quả ────┐          └── spark-submit (thoát sau khi gửi)
        │                       │                     │
        ▼                       │                     ▼
[Cluster]                       │        [Cluster]
  Executor 1 ───────────────────┤          Driver  ◄── nằm TRONG cluster
  Executor 2 ───────────────────┤            ├── Executor 1
  Executor 3 ───────────────────┘            ├── Executor 2
                                             └── Executor 3
```

### A.2. `--deploy-mode client`

Driver chạy **ngay trên máy gõ lệnh `spark-submit`**. Máy submit trở thành một
thành phần đang chạy của ứng dụng.

**Đặc điểm**

- Log của Driver, `print()`, stack trace hiện thẳng ra terminal.
- Kết quả của action (`collect()`, `take()`, `show()`) hiển thị trực tiếp.
- Toàn bộ lưu lượng điều phối (task scheduling, heartbeat, kết quả) đi qua
  đường mạng giữa máy submit và cluster.
- **Nếu tắt terminal hoặc mất mạng, ứng dụng chết.** Driver không còn thì
  Executor cũng bị thu hồi.
- Máy submit phải cho phép Executor kết nối ngược về Driver — thường không khả
  thi nếu máy submit ở sau NAT/VPN hoặc firewall chặn inbound.
- Driver dùng CPU/RAM của máy cá nhân. `collect()` trên tập lớn sẽ gây OOM ở
  chính laptop, không phải ở cluster.

**Dùng khi:** phát triển, gỡ lỗi, chạy thử, demo, notebook tương tác
(`spark-shell`, `pyspark`, Jupyter — các công cụ này **chỉ** chạy được ở
client mode vì cần vòng lặp REPL tương tác).

### A.3. `--deploy-mode cluster`

Cluster Manager cấp phát một container/node trong cluster để chạy Driver.
`spark-submit` chỉ đóng vai trò gửi đơn rồi thoát.

**Đặc điểm**

- Máy submit **có thể tắt** ngay sau khi submit; job vẫn chạy tiếp.
- Driver nằm cùng mạng nội bộ với Executor → độ trễ điều phối thấp hơn nhiều,
  đặc biệt với job có nhiều task nhỏ.
- Driver dùng tài nguyên của cluster, khai báo qua `--driver-memory` /
  `--driver-cores`.
- **Không thấy log trực tiếp.** Phải lấy qua Spark History Server, `yarn logs
  -applicationId <id>`, hay `kubectl logs`.
- Cluster Manager có thể **tự khởi động lại Driver** khi nó chết
  (ví dụ `--supervise` ở Standalone, `spark.yarn.maxAppAttempts` ở YARN).
- File phụ thuộc (script Python, file cấu hình, dữ liệu) phải nằm ở nơi cluster
  truy cập được (HDFS, S3) hoặc được đóng gói gửi kèm — **không** thể trỏ tới
  đường dẫn cục bộ trên máy submit.

**Dùng khi:** chạy production, job dài, job theo lịch, job submit từ CI/CD hoặc
từ máy không đảm bảo online liên tục.

### A.4. Bảng so sánh

| Tiêu chí | `client` | `cluster` |
|---|---|---|
| Vị trí Driver | Máy submit | Node trong cluster |
| Vị trí Executor | Trong cluster | Trong cluster |
| Xem log Driver | Trực tiếp trên terminal | Qua History Server / `yarn logs` / `kubectl logs` |
| Tắt máy submit | Ứng dụng chết | Ứng dụng vẫn chạy |
| Độ trễ mạng điều phối | Cao (qua WAN/VPN) | Thấp (trong cùng cluster) |
| Tài nguyên Driver | CPU/RAM máy cá nhân | Tài nguyên cluster |
| Tự khởi động lại Driver | Không | Có (nếu bật) |
| Yêu cầu mạng | Executor phải kết nối ngược về máy submit | Không cần |
| Vị trí file phụ thuộc | Đường dẫn cục bộ dùng được | Phải ở nơi chia sẻ được (HDFS/S3) |
| Hỗ trợ shell tương tác | Có | Không |
| Trường hợp dùng | Dev, debug, demo | Production, job theo lịch |

> **Lưu ý:** `--deploy-mode` **không** liên quan tới `--master local[*]`.
> `local` không có cluster nào cả — Driver và Executor cùng nằm trong một JVM
> trên một máy. Khi `--master local[*]` thì `--deploy-mode` bị bỏ qua.

## B. Ba Cluster Manager

**Cluster Manager** là thành phần cấp phát tài nguyên (CPU, RAM, container) cho
ứng dụng Spark. Nó trả lời câu hỏi *"lấy máy ở đâu để chạy Driver và Executor"*,
tách biệt với câu hỏi *"Driver chạy ở đâu"* (deploy mode).

> Mesos từng là Cluster Manager thứ tư nhưng đã bị **deprecated từ Spark 3.2 và
> gỡ bỏ ở Spark 4.0**, nên không đưa vào đây.

### B.1. Standalone

Cluster Manager đi kèm sẵn trong bản phân phối Spark, gồm tiến trình **Master**
và các tiến trình **Worker**. Không cần cài thêm gì ngoài Spark và JVM.

| | |
|---|---|
| **Ưu điểm** | Cài đặt đơn giản nhất, gọn nhẹ, ít thành phần phải vận hành. Phù hợp cluster chỉ chạy Spark. |
| **Nhược điểm** | Chỉ chạy được Spark — không chia sẻ tài nguyên với Hive, Flink, MapReduce... Cơ chế hàng đợi và phân quyền rất sơ khai (mặc định là FIFO). Master là điểm chết đơn lẻ nếu không cấu hình HA bằng ZooKeeper. |
| **Dùng khi** | Cluster nhỏ/vừa dành riêng cho Spark, môi trường học tập, PoC. |

```bash
--master spark://<master-host>:7077
```

Hỗ trợ cả `client` và `cluster` mode. Ở `cluster` mode có cờ `--supervise` để
tự khởi động lại Driver khi nó chết.

### B.2. YARN (Hadoop YARN)

Bộ quản lý tài nguyên của hệ sinh thái Hadoop. Spark chạy như một ứng dụng YARN
thông thường, trong đó **ApplicationMaster** đàm phán container với
**ResourceManager**.

| | |
|---|---|
| **Ưu điểm** | Chín muồi trong môi trường doanh nghiệp. Chia sẻ cluster giữa Spark, Hive, MapReduce... Có hàng đợi phân cấp, quota, ưu tiên (Capacity/Fair Scheduler). Tích hợp sẵn Kerberos để xác thực. Gần dữ liệu HDFS nên tận dụng được data locality. |
| **Nhược điểm** | Phải vận hành cả một cụm Hadoop. Cấu hình phức tạp. Container dùng chung thư viện ở tầng host nên khó cô lập phụ thuộc giữa các job. |
| **Dùng khi** | Tổ chức đã có sẵn Hadoop/HDFS, nhiều nhóm dùng chung một cluster. |

```bash
--master yarn --deploy-mode cluster
```

Ở `cluster` mode, Driver chạy **bên trong** ApplicationMaster. Ở `client` mode,
ApplicationMaster chỉ làm nhiệm vụ xin container, còn Driver ở máy submit.

### B.3. Kubernetes

Từ Spark 3.1, hỗ trợ Kubernetes đã **generally available** (không còn
experimental). Driver và mỗi Executor chạy trong một **Pod** riêng.

| | |
|---|---|
| **Ưu điểm** | Cô lập phụ thuộc triệt để — mỗi job mang container image riêng, không xung đột phiên bản Python/thư viện. Hợp với hạ tầng cloud-native và CI/CD. Tự co giãn (dynamic allocation qua shuffle tracking). Dùng chung cluster với dịch vụ web, ML serving... |
| **Nhược điểm** | Cần biết vận hành Kubernetes. Thời gian khởi động Pod làm tăng độ trễ cho job ngắn. Shuffle service và lưu trữ tạm phải cấu hình thêm (chưa mượt như YARN). Ít công cụ quản trị theo hàng đợi bằng YARN. |
| **Dùng khi** | Hạ tầng đã container hóa, cần cô lập môi trường, triển khai đa đám mây. |

```bash
--master k8s://https://<api-server>:<port> \
--deploy-mode cluster \
--conf spark.kubernetes.container.image=<image>
```

Kubernetes **chủ yếu dùng `cluster` mode**. `client` mode có hỗ trợ nhưng yêu
cầu Driver chạy trong một Pod có địa chỉ mà Executor gọi ngược về được
(thường qua headless Service).

### B.4. Bảng so sánh

| Tiêu chí | Standalone | YARN | Kubernetes |
|---|---|---|---|
| Cần cài thêm | Không (kèm Spark) | Cụm Hadoop | Cụm Kubernetes |
| Chia sẻ với framework khác | Không | Có (Hive, MR, Flink) | Có (mọi workload container) |
| Cô lập phụ thuộc | Yếu | Trung bình | Mạnh (container image) |
| Quản lý hàng đợi / quota | Sơ khai (FIFO) | Mạnh (Capacity/Fair) | Qua namespace + quota |
| Bảo mật / xác thực | Cơ bản | Kerberos | RBAC + Secret |
| Độ phức tạp vận hành | Thấp | Cao | Cao |
| Data locality với HDFS | Nếu cùng node | Tốt nhất | Yếu (lưu trữ tách rời) |
| Deploy mode hỗ trợ | client + cluster | client + cluster | chủ yếu cluster |
| `--master` | `spark://host:7077` | `yarn` | `k8s://https://host:port` |

### C.2. Điểm cần lưu ý khi chuyển sang `cluster` mode

1. **Đường dẫn dữ liệu.** Hiện `generate_logs.py` ghi ra
   `data/raw/raw_logs.txt` — đường dẫn *tương đối* so với thư mục repo. Ở
   `cluster` mode, Driver chạy trên node khác nên đường dẫn này **không tồn
   tại**. Cần truyền đường dẫn input qua tham số và trỏ tới HDFS/S3, hoặc gửi
   kèm file bằng `--files`.
2. **Đọc Accumulator.** `invalid_log_counter.value` chỉ đọc được ở Driver. Ở
   `cluster` mode, `print()` của Driver đi vào log của cluster chứ không ra
   terminal — nếu muốn giữ lại con số này thì nên ghi ra file kết quả trong
   `data/output/` thay vì chỉ `print()`.
3. **Kích thước Broadcast.** Bảng `ip_country_map` hiện rất nhỏ (16 tiền tố
   `/24`) nên không có rủi ro bộ nhớ ở bất kỳ mode nào.
4. **Phiên bản Python.** Ở `cluster` mode, phiên bản Python trên node có thể
   khác máy submit. Cần đặt `PYSPARK_PYTHON` cho khớp, nếu không Executor sẽ
   lỗi khi deserialize.

### C.3. ĐÃ KIỂM CHỨNG BẰNG THỰC NGHIỆM: phải dùng `--py-files`

> Đây **không phải suy đoán**. Lỗi dưới đây đã tái hiện được trên máy, 3/3 lần.

Trên **PySpark 3.5** (phiên bản mà `requirements.txt` của repo đang pin:
`pyspark>=3.5,<4`), Python worker **không kế thừa `sys.path` của Driver**. Hệ
quả: nếu chạy job từ thư mục khác gốc repo, worker chết ngay ở stage 0 với
`Connection reset by peer` phía JVM — thực chất là `ModuleNotFoundError` phía
Python worker khi nó cố unpickle hàm tham chiếu tới module `rdd_processing`.

Đối chiếu hai phiên bản, cùng một code, cùng một dữ liệu:

| Phiên bản | Chạy từ gốc repo | Chạy từ thư mục khác |
|---|---|---|
| PySpark 4.2.0 | 5/5 PASS | 5/5 PASS (worker kế thừa `sys.path`) |
| **PySpark 3.5.9** | **3/3 PASS** | **0/3 — worker chết** |

Vì nhóm đang pin `<4`, đây là hành vi thực tế mà `submit_job.sh` phải xử lý:

```bash
spark-submit \
  --master <master> \
  --deploy-mode cluster \
  --py-files src/rdd_processing.py,src/generate_logs.py \
  src/main.py --input <duong-dan-input>
```

Ở `local` mode có thể tạm né bằng cách luôn phát lệnh từ gốc repo, nhưng cách
đó **không** dùng được ở `cluster` mode vì worker nằm trên máy khác. Không có
`--py-files`, job sẽ chết ngay khi rời khỏi `local`.
